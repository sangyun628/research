엔지니어를 위한 TL;DR
Graph RAG는 "벡터 유사도 1-hop 검색"의 한계(멀티홉 추론·전역 요약·관계 질의)를 구조화된 그래프 + 커뮤니티 요약으로 보강한다. 온톨로지(RDF/OWL/SHACL)는 그 그래프에 스키마·제약·추론을 부여해 신뢰성을 높인다. 에이전트는 이 그래프를 장기 메모리이자 도구(MCP)로 삼아 읽고 쓴다. 단, 인덱싱 비용과 점진적 업데이트가 핵심 트레이드오프다.

01왜 Graph RAG인가 — Vector RAG의 구조적 한계

표준(naive) RAG는 "청크 임베딩 → top-k 코사인 유사도 → 컨텍스트 주입"이다. 이 단순함이 강력하지만, 세 가지 질의 유형에서 구조적으로 약하다.

① 멀티홉 추론

"A의 공급사가 투자한 회사의 CEO는?" 같은 질문은 여러 문서를 연결해야 답이 나온다. 벡터 검색은 각 청크를 독립적으로 보기 때문에 연결 고리가 같은 청크에 없으면 실패한다.

② 전역 요약 (sense-making)

"이 코퍼스 전체의 핵심 테마 5가지는?" 같은 질문은 top-k로는 답할 수 없다. 전체 구조를 조망해야 하는데, 벡터 검색은 국소적이다.

③ 관계·집계 질의

"이 사람과 직·간접적으로 연결된 모든 프로젝트"처럼 관계 자체가 답인 질문. 그래프 순회(traversal)·집계가 본질적으로 필요하다.

벡터 RAG vs Graph RAG 패러다임 비교

균형 잡힌 시각
Graph RAG가 만능은 아니다. GraphRAG-Bench(ICLR'26)와 여러 연구는 단순 사실 검색(fact lookup)에서는 벡터 RAG가 더 싸고 충분히 정확하며, 일부 실무 태스크에서 GraphRAG가 vanilla RAG보다 못한 경우도 보고한다. Graph RAG의 가치는 질의 복잡도에 비례한다.

04Retrieval 전략 — Local · Global · DRIFT · Hybrid

"무엇을 그래프에서 가져올 것인가(node·triple·path·subgraph)"와 "어떤 검색 모드를 쓸 것인가"가 응답 품질을 결정한다. 실무에서는 질의 라우팅 + 하이브리드가 정석이다.

Local Search

특정 엔티티를 시드로 이웃·관계·연관 텍스트로 fan-out. "X에 대해 자세히" 류의 구체적 질문에 강함. 검색 범위가 좁아 빠르고 저렴.

Global Search

커뮤니티 요약을 map-reduce로 종합. "전체 코퍼스의 주요 테마는?" 류 sense-making에 필수. 요약을 다 읽으므로 토큰 비용이 큼.

DRIFT Search

Global의 광역성과 Local의 정밀성을 동적으로 혼합. 커뮤니티에서 시작해 관련 엔티티로 drift-in. MS GraphRAG의 권장 기본값.

그래프에서 무엇을 검색하는가 — 검색 단위

실무 권장: Hybrid + Router
프로덕션 RAG는 벡터 검색(빠른 사실)·그래프 순회(관계/멀티홉)·커뮤니티 요약(전역)을 모두 두고, 라우팅 레이어가 질의를 분류해 적절한 경로로 보낸다. 예: 단순 질의→벡터, 멀티홉→PPR/path, "요약/전체"→global. Lettria 사례에선 Qdrant(벡터)+Neo4j(그래프) 하이브리드로 정확도 약 20%p 개선이 보고됐다.

05온톨로지 & 지식그래프 모델링 — RDF · OWL · SHACL

LLM이 추출한 "노이즈 그래프"와, 시맨틱 웹 표준(W3C)으로 설계된 "온톨로지 기반 KG"는 다르다. 후자는 스키마·제약·논리적 추론(reasoning)을 제공해 검증 가능하고 신뢰성 있는 지식을 만든다.

시맨틱 웹 스택

OWL vs SHACL — 자주 혼동되는 둘

구분OWL (Web Ontology Language)SHACL (Shapes Constraint Language)
목적도메인 모델링 + 논리적 추론RDF 데이터 구조 검증
가정Open World (명시 안 된 것 = 미지)Closed World (명시 안 된 것 = 위반)
전형적 용도"A는 B의 하위클래스 → A 인스턴스는 B다" 추론"Person은 반드시 name 1개를 가진다" 검증
결과새로운 사실 도출(entailment)위반 리포트(conformance)
엔지니어 관점타입 시스템 + 추론 엔진스키마 validator / 단위 테스트
2025 실무 합의
최신 연구(KCAP'25 등)는 OWL로 도메인 모델링 + SHACL로 검증의 조합을 권장한다. 최소 실행안은 "SHACL 구조 검증"이고, 여기에 "OWL Reasoner로 논리 일관성 체크"를 더하면 신뢰성이 올라간다. LLM 파이프라인에선 추출 직후 SHACL/OWL 제약으로 트리플을 게이트키핑한다.

06LLM 기반 지식그래프 구축 — Schema-based vs Schema-free, EDC

LLM-empowered KG construction 서베이(arXiv 2510.20345)는 두 패러다임을 구분한다. 실무에선 둘을 절충한 EDC(Extract–Define–Canonicalize) 3단계 파이프라인이 표준으로 자리잡고 있다.

Schema-based (온톨로지 주입)

미리 정의한 온톨로지를 LLM에 주고 그 스키마로 인스턴스화. 일관성·정렬·검증이 쉽고 다운스트림 추론에 유리. 반면 스키마 밖 지식은 놓친다. Wikidata schema 기반 KG 구축이 대표 사례.

Schema-free (open extraction)

LLM이 엔티티·관계를 자율적으로 추론. 유연하고 커버리지가 넓지만 동의어·중복·불일치 노이즈가 큼. 사후 정규화(canonicalize)가 필수.

EDC 파이프라인 — 추출에서 정규화까지

엔티티 해소(Entity Resolution) — 그래프 품질의 핵심

LLM 추출 KG의 가장 큰 적은 중복 엔티티와 부정확한 관계다. "IT" vs "Information Technology", "2024" vs "Year 2024"를 다른 노드로 두면 그래프가 파편화된다. MS GraphRAG·LightRAG는 기본적으로 단순 문자열 매칭을 쓰지만, 고품질이 필요하면 다음 파이프라인을 쓴다.

단계기법설명
Blocking후보 축소전체 비교(O(n²)) 대신 키/임베딩 버킷으로 비교 대상 좁힘

전문가 주석 데이터셋에서 LLM 엔티티 추출은 정밀도 98.8% / 재현율 93.2% / F1 95.9% 수준. 온톨로지 매칭에서 GPT-4o는 BERTMap 대비 정밀도 +44.9%p, F1 +38.3%p 향상이 보고됐다. 단, 관계 추출 정밀도는 보통 75%대로 엔티티보다 낮아 검증 단계가 중요하다.

Graph RAG 스택은 4개 레이어로 나뉜다: 저장소(그래프/벡터 DB) · 오케스트레이션 · RAG 프레임워크 · 메모리/시간그래프. 각 레이어의 대표 OSS와 선택 기준을 정리한다.

08에이전트 시스템 통합 — Agentic GraphRAG · MCP · 그래프 메모리

에이전트 엔지니어에게 그래프/온톨로지는 두 가지로 쓰인다: (1) 추론을 위한 검색 도구, (2) 읽고 쓰는 장기 메모리. GraphRAG는 에이전트가 KG를 자율적으로 검색·기록할 때 "agentic"이 된다.

Agentic RAG 오케스트레이션 패턴

Single-Agent

한 에이전트가 데이터 소스(벡터/그래프/요약)를 스스로 선택. 가장 단순한 라우팅형.

Multi-Agent

코디네이터가 도메인별 sub-agent에 하위작업 위임, 공유 메모리로 상태 전달.

Hierarchical

계층 티어로 에이전트 조직화. master가 분해, sub가 도메인 모델·메모리 보유.

Graph-based

KG/구조적 추론을 코어로. neural-symbolic, 그래프 메모리, 평가-최적화 루프 결합.

레퍼런스: MCP로 그래프를 에이전트에 연결

MCP(2024.11 공개)는 RAG/GraphRAG를 MCP 서버로 노출해 에이전트가 표준 방식으로 검색·기록하게 한다. Neo4j는 2024.12 최초의 데이터 레벨 MCP 통합을 냈고, mcp-neo4j-memory는 엔티티·관찰·관계를 저장하고 관련 서브그래프를 검색한다.

예: LangGraph 에이전트가 GraphRAG MCP 도구를 호출하는 골격

# 에이전트가 질의 의도에 따라 그래프/벡터/메모리 도구를 라우팅
from langgraph.graph import StateGraph, END

def route(state):
    q = state["query"]
    if is_global(q):       return "global_summary"   # 커뮤니티 요약 map-reduce
    if is_multihop(q):     return "graph_traverse"   # PPR / path 검색 (MCP: search_graph)
    return "vector_lookup"                          # 단순 사실 → 벡터

def graph_traverse(state):
    sub = mcp.call("search_graph", seeds=extract_entities(state["query"]))
    return {"context": rank_and_prune(sub)}

def reflect(state):
    # 근거 부족 시 재검색, 새 사실은 메모리에 기록 (bi-temporal)
    if not grounded(state): return "graph_traverse"
    mcp.call("write_memory", facts=state["new_facts"], valid_at=now())
    return END

g = StateGraph(dict)
g.add_node("graph_traverse", graph_traverse); g.add_node("reflect", reflect)
g.set_conditional_entry_point(route)            # 질의 라우팅
g.add_edge("graph_traverse", "reflect")        # 검색 → 성찰 루프
agent = g.compile(checkpointer=memory)          # 상태 영속화

그래프 = 에이전트의 장기 메모리 (Temporal KG)

대화·관찰을 KG로 누적하면 관계 기반 회상이 가능하다. 핵심은 시간성이다. Graphiti/Zep의 bi-temporal 모델은 각 엣지에 4개 타임스탬프를 둔다.

타임스탬프의미용도
t_valid / t_invalid사실이 현실에서 유효한 구간"그때는 맞았다" — 과거 상태 질의
t_created / t_expired사실이 시스템에 기록·폐기된 시점provenance·감사, 잘못된 입력 추적
왜 중요한가
새 정보가 기존과 충돌할 때, 옛 사실을 삭제하지 않고 invalidate한다. 에이전트는 "현재 사실"과 "과거 사실"을 구분해 회상할 수 있다. Zep은 DMR 벤치 94.8%(MemGPT 93.4% 상회), LongMemEval에서 정확도 최대 +18.5%p 향상과 응답 지연 90% 감소를 보고했다.

10아키텍처 의사결정 가이드

"Graph RAG를 써야 하나?"에 대한 실무 결정 트리. 핵심 변수는 질의 복잡도 · 코퍼스 변동성 · 신뢰성 요구 · 예산이다.

한 줄 휴리스틱
"검색 결과가 사람이 읽고 끝"이면 RAG 품질만, "에이전트가 그 위에서 추론·행동"이면 그래프 구조 + 메모리가 ROI를 낸다. 그래프의 가치는 질의 복잡도와 멀티스텝성에 비례한다.

11레퍼런스 스택 — 에이전트 엔지니어를 위한 권장 조합

위 모든 결정을 종합한, 2026년 기준 "무난한 시작점" 두 가지. 작게 시작해 필요할 때 레이어를 더한다.

A. 실용형 (빠른 출시·비용 우선)

  • 저장소: Qdrant(벡터) + Neo4j(그래프), ID 교차참조
  • 인덱싱: LightRAG 또는 LazyGraphRAG (증분/저비용)
  • 검색: 라우터로 벡터/그래프/요약 하이브리드
  • 오케스트레이션: LangGraph (상태·reflection 루프)
  • 메모리: Graphiti(시간그래프) — 필요 시
  • 노출: 검색·기록을 MCP 서버로

B. 신뢰형 (규제·정합성 우선)

  • 모델링: OWL 온톨로지 + RDFS 스키마
  • 저장소: RDF Triplestore(GraphDB) + 벡터 DB
  • 구축: EDC 파이프라인(스키마 기반), Wikidata 정렬
  • 검증: SHACL 형태 검증 + OWL Reasoner 일관성
  • 품질: 엔티티 해소 + triple reflection
  • 질의: SPARQL + GraphRAG 하이브리드
점진적 도입 로드맵
1) 벡터 RAG로 베이스라인 → 2) 실패 질의(멀티홉/전역) 분석 → 3) 해당 질의에만 그래프 경로 추가(하이브리드) → 4) 에이전트가 쓰기 시작하면 시간그래프 메모리 → 5) 신뢰성 요구가 생기면 온톨로지·SHACL 게이트. 처음부터 full GraphRAG로 시작하지 말 것 — 비용이 가장 흔한 실패 원인이다.
