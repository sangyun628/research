# Jevlike·OpenJev의 속도와 인프라 비용 — 일반 LLM 대비 효과

분석일: 2026-09-18. 코드 기준은 Jevlike `94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452`, OpenJev `53e3028363509f8533d90fe82d983770da1f6c02`다. 구조·학습 지원은 [기존 비교](jevlike-vs-openjev.md)를 참고한다.

수치는 **작성자 공개 실험**, **이번 로컬 측정**, **산술 추정**으로 구분했다. OpenJev·Jevlike·일반 LLM을 같은 하드웨어와 실제 업무 데이터로 실행한 동등 품질 비교는 아니다.

## 1. 먼저 나눠야 할 세 가지 구성

Jevlike는 Tiny와 HF 구성이 매우 달라서 하나의 비용으로 취급할 수 없다.

| 구성 | 실제 계산 | 주된 절감 지점 | 아직 필요한 자원 |
|---|---|---|---|
| 일반 생성형 LLM | 입력 처리 후 답변 토큰을 순차 생성 | 비교 기준 | 전체 모델, 입력·출력 계산, cache |
| OpenJev | 기존 LLM의 후보 토큰 점수 추출 | 긴 출력 생성 생략, 같은 상태의 입력 계산 재사용 | 기존 LLM 전체와 추론 메모리 |
| Jevlike HF | 동결 인코더로 문맥·후보 인코딩 후 학습한 head 실행 | 출력 생성 생략, 작은 인코더 선택 가능 | 인코더 전체, 후보 인코딩, head |
| Jevlike Tiny | 작은 byte embedding과 attention head | 큰 언어모델 자체를 쓰지 않음 | CPU·메모리, 자체 학습 데이터 |

**OpenJev는 주로 시간을 줄이고, Jevlike Tiny는 모델 크기까지 크게 줄일 수 있다.** 반면 Tiny에는 범용 LLM과 같은 언어 이해·추론 능력을 기대할 수 없으며, 실제 업무를 처리할 수 있을 때만 대체 비용 절감이 의미 있다.

## 2. OpenJev는 일반 LLM 대비 얼마나 빠른가

### 2.1 같은 4B 모델의 두 출력 경로 — 공개 실험

작성자가 동일 Qwen3.5-4B BF16, 동일 상태와 21개 이진 질문, RTX 3090 한 장으로 비교한 결과다. 모델 로딩·warmup은 제외했고 세 번 실행한 wall time 중앙값이다.

| 항목 | 일반 LLM의 간결한 JSON 배열 생성 | OpenJev 병렬 direct |
|---|---:|---:|
| 21개 판단 전체 완료 | 5.3317초 | 1.0230초 |
| 생성된 답변 토큰 | 111 | 0 |
| 전체 시간을 21개로 나눈 처리시간 | 253.89ms | 48.72ms |
| PyTorch 최고 GPU 할당 메모리 | 8.45GiB | 10.81GiB |

계산하면 **약 5.21배 빠르고, 동일 작업의 wall time은 약 80.8% 감소**했다. 그러나 최고 GPU 할당 메모리는 **약 28.0% 증가**했다. OpenJev의 이 경로는 공통 cache를 여러 질문으로 분기해 병렬 처리하기 때문에, 빨라져도 더 작은 GPU에 들어간다고 단정할 수 없다.

근거: [원시 결과 JSON](https://github.com/TheoLeeCJ/openjev/blob/53e3028363509f8533d90fe82d983770da1f6c02/results/raw/decision-vs-compact-array.json), [측정 코드](https://github.com/TheoLeeCJ/openjev/blob/53e3028363509f8533d90fe82d983770da1f6c02/benchmarks/decision_vs_generation.py#L128-L145), [결과 설명](https://github.com/TheoLeeCJ/openjev/blob/53e3028363509f8533d90fe82d983770da1f6c02/docs/RESULTS.md#systems-benchmark).

수치를 해석할 때 다음을 함께 봐야 한다.

- **48.72ms는 독립된 질문 하나의 요청 지연시간이 아니다.** 21개를 묶어 처리한 시간을 나눈 값이다. 이 실행의 완료 지연시간은 약 1.023초다.
- 두 방식의 선택 결과는 21개 중 18개가 같았다. 출력 동작이 다르고 의미상 동일성을 보장하지 않는다.
- 상태와 질문 내용은 같지만 prompt 배치가 다르다. 생성 경로는 하나의 prompt로 배열을 출력하고, direct는 공통 prefix에 질문별 suffix를 붙여 처리한다.
- GPU 메모리는 `torch.cuda.max_memory_allocated()` 값이다. 전체 드라이버 메모리·예약 메모리나 최소 필요 VRAM의 정확한 수치는 아니다.
- 이는 작성자 구현끼리의 비교다. 최적화된 모든 생성형 LLM 서버보다 항상 5.21배 빠르다는 뜻이 아니다.

### 2.2 공통 입력 cache의 효과 — 별도 공개 실험

37개 상태마다 21개 질문을 수행한 777개 판단의 결과다. 상태는 대략 8,000자 규모로 반복 입력의 비중이 크다.

| OpenJev 실행 방식 | 777개 판단 전체 시간 | 처리량 |
|---|---:|---:|
| 매 판단마다 입력을 새로 처리 | 333.1초 | 2.33 decisions/s |
| 상태 prefix 재사용, 질문 순차 실행 | 72.3초 | 10.75 decisions/s |
| 상태 prefix 재사용, 질문 병렬 실행 | 38.8초 | 20.03 decisions/s |

fresh 대비 병렬 경로는 약 **8.59배** 빠르다. 이것은 앞의 5.21배와 다른 비교다. **둘을 곱해 44배 절감이라고 계산하면 안 된다.** 이 실험에서는 계산 형태에 따라 fresh 대비 5~6개의 argmax 변화도 관측됐다. [측정 조건](https://github.com/TheoLeeCJ/openjev/blob/53e3028363509f8533d90fe82d983770da1f6c02/docs/METHOD.md#shape-matched-systems-benchmark).

같은 고객 기록·문서에 여러 질문을 던지는 작업에서는 유리하다. 매번 완전히 다른 입력에 단일 질문만 처리한다면 이 정도의 cache 효과는 없다. 일반 LLM 서버도 prefix caching을 지원할 수 있다. 예를 들어 vLLM APC는 공통 prefix의 입력 처리를 재사용한다. 따라서 이미 cache·batching을 적용한 서버와 비교하면 차이가 줄 수 있다. [vLLM 공식 APC 설명](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/).

### 2.3 기존 LLM이 A 한 글자만 출력한다면?

이 경우 direct readout의 출력 생략 이득은 작을 수 있다. 같은 모델·같은 prompt에서 첫 답변 토큰의 분포는 입력 처리 과정에서 이미 계산되기 때문이다.

```text
일반 LLM에서 m개 출력 토큰 생성:
  입력 처리 + 첫 토큰 선택 + 후속 m-1회 decode + 부가 처리

OpenJev direct:
  입력 처리 + 허용 후보 logits 추출·정규화
```

수십·수백 토큰을 생성하던 것을 후보 점수로 바꾸면 효과가 크다. 이미 답변을 단일 토큰으로 제한했다면 대규모 decode 절감 여지가 없다. 대신 후보 전체의 상대 점수를 직접 얻는 장점은 남는다.

긴 reasoning을 없애 얻는 속도는 판단 품질과 함께 봐야 한다. 복잡한 문제에 필요한 reasoning까지 생략하고 동등한 정확도를 가정할 수는 없다.

## 3. Jevlike는 얼마나 가벼운가

### 3.1 Tiny CPU 지연시간 — 이번 직접 측정

이전 분석에서 학습한 기본 Tiny checkpoint로 측정했다. 하드웨어는 Apple M5·RAM 32GB이며 **GPU를 사용하지 않고 CPU만 사용**했다. Python 3.13.2, PyTorch 2.14.0, intra-op 2 threads, inter-op 1 thread, batch size 1이다.

각 조건마다 100회 warmup 후 1,200회 측정했다. UTF-8 변환·batch tensor 구성·forward·softmax·Python list 변환을 포함한다. 모델 로딩, HTTP, 요청 대기, JSON 응답 직렬화는 제외했다.

| 입력 조건 | 평균 | p50 | p95 |
|---|---:|---:|---:|
| 제공 합성 데이터 400행 순환, 문맥 101~118 bytes, 후보 2~8개 | 0.109ms | 0.102ms | 0.147ms |
| 고정 192-byte 문맥, 후보 8개 | 0.133ms | 0.127ms | 0.174ms |

| 자원 항목 | 측정값 |
|---|---:|
| 파라미터 수 | 41,280 |
| FP32 파라미터 tensor 합계 | 165,120 bytes — 약 0.165MB |
| checkpoint 파일 | 169,063 bytes |
| 실행 프로세스 최고 RSS | 226,230,272 bytes — 약 226MB |

**작은 가중치 파일이 프로세스 전체 메모리라는 뜻은 아니다.** Python·PyTorch 런타임을 포함한 메모리가 별도로 든다. 그래도 이번 짧은 입력에서는 별도의 GPU 없이 추론할 수 있었다.

재현용 스크립트와 원시 결과는 git에서 제외된 클론 안에 있다.

```text
.repos/jevlike/runs/research/latency_benchmark.py
.repos/jevlike/runs/research/latency.json
```

클론 루트에서 `.venv/bin/python runs/research/latency_benchmark.py`로 실행한다. 학습 checkpoint 및 합성 데이터 생성 명령은 [학습 가이드](../jevlike/training-and-finetuning.md#6-이번에-실행한-실험)에 있다.

**이 0.1ms와 OpenJev의 48.7ms를 나눠 성능 우위를 주장하면 안 된다.** 하드웨어·문맥 길이·질문 묶음·모델 능력이 다르다. Tiny는 byte 수준의 작은 선택기이고 OpenJev 예시는 4B LLM이다. Tiny의 합성 데이터 정확도 99.75% 역시 긴 문서의 업무 판단 정확도를 의미하지 않는다.

### 3.2 HF 인코더 구성 — 아직 직접 지연시간 미측정

Jevlike의 HF 예시인 Qwen2.5-0.5B는 약 0.49B 파라미터다. 가중치만 단순 계산하면 16bit 약 0.98GB, FP32 약 1.96GB이며 head와 실행 공간은 추가된다. Jevlike 코드에 명시적인 dtype·양자화 설정이 없으므로 16bit 메모리를 기본 실측치로 제시할 수는 없다. [Qwen 모델 카드](https://huggingface.co/Qwen/Qwen2.5-0.5B), [Jevlike HF 인코더 코드](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/jevlike/model.py#L66-L94).

**head만 학습한다는 사실은 추론 때 head만 실행한다는 뜻이 아니다.** 매 요청마다 인코더가 문맥과 후보를 처리한다. 동결은 학습 시 역전파·optimizer 비용을 줄이고, 추론 시 인코더 forward 비용은 남긴다.

기본 코드에는 문맥 인코딩 1회와 후보 배치 인코딩 1회가 있으며 후보 embedding cache는 없다. 같은 인코더를 쓴 OpenJev와 비교하더라도 어느 쪽이 더 빠른지는 후보 수·후보 길이·문맥 길이·batch 형태에 따라 달라진다.

0.5B와 4B의 파라미터 규모가 약 8배 다르더라도 속도·비용·품질이 같은 비율로 변하지 않는다. OpenJev에도 더 작은 모델을 사용할 수 있으므로 “Jevlike는 항상 0.5B, OpenJev는 항상 4B”가 고정된 조건도 아니다.

### 3.3 Jevlike의 100배 주장 범위

상류 README에는 8개 후보를 처리할 때 400개 토큰을 강제로 생성하는 소형 decoder보다 약 100배 빨랐다는 설명이 있다. 출력 길이와 조건이 크게 달라서, 이를 “최적화된 객관식 LLM보다 100배 빠르다”거나 “OpenJev보다 100배 빠르다”로 해석할 수 없다. [상류 설명](https://github.com/vinnylarouge/jevlike#what-to-expect).

## 4. GPU 요금으로 환산하면

### 4.1 같은 작업을 모아서 처리하고 종료하는 경우

2026-09-18 확인한 Runpod 공개 가격표의 RTX 3090 요금 **$0.50/시간**을 계산 예시로 사용한다. 특정 가용 인스턴스의 견적이나 동일 처리 속도 보장은 아니다. [공식 가격표](https://www.runpod.io/pricing).

아래는 공개 실험의 **같은 상태에 21개 판단을 묶는 패턴**을 100만 개 개별 판단으로 선형 환산한 산술 예시다. GPU가 필요한 작업을 계속 처리하고, 작업이 끝나면 종료한다고 가정한다.

```text
활성 인스턴스 시간 = (100만 판단 ÷ 21) × 21개 판단 처리시간 ÷ 3600
환산 요금 = 활성 인스턴스 시간 × $0.50
```

| 경로 | 100만 판단에 필요한 활성 시간 | 활성 시간만 환산한 요금 |
|---|---:|---:|
| 일반 4B LLM의 간결한 배열 생성 | 약 70.53시간 | 약 $35.26 |
| OpenJev 병렬 direct | 약 13.53시간 | 약 $6.77 |

약 80.8% 감소는 이 조건에서의 **처리시간 기반 환산**이다. 다음은 포함하지 않았다.

- cold start·모델 다운로드·로딩·warmup·유휴 시간
- 별도 청구되는 저장 공간·네트워크·서비스 인프라
- 개발 비용, 잘못된 판단에 대한 재처리와 fallback 비용
- 부하 변화, SLA를 위한 여유 용량, 이중화

또한 100만 개 독립 문서에 한 질문씩 던지는 작업은 이 패턴이 아니다. 그 경우 21-way 공통 상태 재사용 가정을 적용할 수 없다. 실제 클라우드 호스트에서 이 벤치마크를 재실행한 비용 측정도 아니다.

### 4.2 GPU를 계속 켜 두는 경우

같은 GPU 한 장을 월 730시간 할당하면 위 단가로 **약 $365/월**이다. 일반 LLM을 실행하든 OpenJev를 실행하든 같은 장비를 같은 시간 동안 유지하면 GPU 인스턴스 기본 요금은 같다.

이때 OpenJev의 이점은 다음 형태로 나타난다.

- 같은 GPU로 더 많은 판단을 처리한다.
- 처리량 증가에 필요한 추가 GPU 수를 늦추거나 줄인다.
- 지연시간을 줄인다.
- 부하가 낮을 때 장비를 내려 실제 할당 시간을 줄일 수 있는 구조라면 비용도 줄인다.

처리가 5배 빨라졌다고 월 고정 GPU 요금이 자동으로 1/5이 되지는 않는다. 전력 소비 역시 wall time만으로 80.8% 감소했다고 단정할 수 없다. 여기서는 실제 GPU 전력·에너지를 측정하지 않았다.

### 4.3 Tiny의 GPU 비용은 0이 될 수 있지만 총비용은 남는다

실제 업무가 Tiny로 충분히 해결되면 CPU 서비스에 올려 전용 GPU 비용을 없앨 수 있다. 반면 CPU·RAM·애플리케이션 서비스 자원, 학습 데이터 라벨링, 학습·재학습 작업은 남는다. 이번 M5의 latency만으로 특정 클라우드 vCPU 처리량이나 월 CPU 요금을 산정하지 않았다.

Jevlike HF는 일반적으로 Tiny보다 자원이 크다. 더 작은 GPU·CPU 실행이 가능할 수 있지만 업무 SLA와 입력 길이에 따라 달라진다. 동일 업무의 지연시간·품질 실측 없이 특정 GPU 등급이나 월 비용을 확정할 수는 없다.

### 4.4 기존 LLM이 외부 API라면

외부 API의 token 요금과 자체 GPU 인스턴스 시간 요금은 직접 같은 비율로 비교할 수 없다. API는 입력·출력 token 수와 해당 모델 요금, 자체 운영은 인스턴스 할당 시간과 이용률이 중요하다.

```text
API 비용 ≈ 입력 token 합계 × 입력 단가 + 출력 token 합계 × 출력 단가
자체 운영 비용 ≈ 인스턴스 할당 시간 × 시간당 단가 + 기타 인프라
Jevlike 도입 총비용 ≈ 자체 운영 비용 + 라벨링·학습·유지보수 비용
```

입력 caching 요금·batch 할인·실패 재시도·fallback이 있으면 추가 반영해야 한다. 트래픽이 드물면 전용 GPU를 상시 운영하는 것보다 API가 저렴할 수 있고, 반복적인 대량 판단에서는 자체 모델이 유리해질 수 있다. 현재 사용 중인 API 모델과 입력·출력 길이가 주어지지 않아 특정 API 대비 절감률은 제시하지 않았다.

## 5. 두 프로젝트를 직접 비교했을 때의 판단

| 판단 항목 | Jevlike Tiny | Jevlike HF | OpenJev 4B 예시 |
|---|---|---|---|
| 모델 자원 규모 | 매우 작음. 기본 41,280 파라미터 | 선택한 인코더가 대부분 차지 | 기존 4B급 LLM 전체 유지 |
| GPU 필요성 | 이번 짧은 입력은 CPU만으로 동작 | 입력·모델·SLA에 따라 결정 | 기본 Python loader는 CUDA 요구 |
| 이번에 확인한 속도 | M5 CPU p50 0.10~0.13ms | 직접 측정하지 않음 | 작성자 21개 판단 전체 약 1.02초 |
| 자체 학습 비용 | Tiny 전체 학습·라벨링 필요 | head 학습·라벨링 필요 | 추가 학습 없이 사용 가능 |
| 범용 자연어 질문 대응 | 제한적인 구조 | 사전학습 표현 + 학습한 선택기 | 기반 LLM의 지시 수행 능력 활용 |
| 같은 상태에 여러 질문 | 기본 재사용 기능 없음 | 기본 재사용 기능 없음 | prefix 재사용·병렬 질문 지원 |
| 주요 비용상 장점 | GPU 제거 가능성 | 작은 인코더로 업무 전문화 가능성 | 기존 LLM의 decode·반복 입력 비용 절감 |

세 구성의 품질이 같은 업무에서 필요한 수준을 충족한다는 조건이라면 Tiny는 가장 큰 자원 절감 후보다. 하지만 기본 Tiny가 그 조건을 만족한다는 근거는 아직 없다. Jevlike HF와 OpenJev는 이름만으로 속도 순위를 정할 수 없다.

판단 오류가 비싼 업무라면 **정확도 기준을 충족한 판단 1건당 비용**과 **큰 모델로 다시 보내는 비율**을 함께 봐야 한다. 저렴한 모델이 대부분의 요청을 다시 큰 모델로 넘기면 기대한 절감 효과가 사라질 수 있다.

## 6. 실제 도입 비용을 결정하는 최소 정보

운영 절차나 QA 계획보다 다음 workload 정의가 비교의 핵심이다.

1. 현재 baseline 모델과 호출 형태: 같은 로컬 모델인가, 외부 API인가, 긴 reasoning을 사용하는가.
2. 입력·후보·출력 길이: 단일 글자 선택인가, 긴 설명·JSON을 생성하는가.
3. 같은 상태에 묶을 수 있는 질문 수: 1개와 21개는 OpenJev cache 효과가 다르다.
4. 월 판단 수·피크 요청률·허용 지연: GPU 유휴 시간과 필요한 장비 수를 결정한다.
5. 필요한 품질과 fallback 비율: 작은 모델로 해결 가능한 요청 비중을 결정한다.

현재 근거로 말할 수 있는 범위는 **OpenJev는 특정 21개 판단 실험에서 약 5.2배 속도 개선**, **Jevlike Tiny는 짧은 입력에서 CPU로 약 0.1ms 처리**, **동등 업무·품질에서 두 프로젝트의 정확한 비용 배수는 아직 미확인**이다.
